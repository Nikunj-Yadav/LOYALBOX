# AI log

Everything below really happened while this project was generated by Claude in one working session. It is not a record of any other AI use. If you used other tools or prompts yourself, add them here before submitting. Nothing in this file has been invented to fill a quota.

Format: **Prompt / action** → **What the AI produced** → **Problem (if any)** → **How it was detected** → **Fix**.

---

### 1. The project brief
**Prompt:** the full LOYALBOX specification (business rules, security rules, stack, design system, documentation, development order).
**Result:** Claude installed PHP 8.3 and MariaDB in its sandbox (neither was present) so it could actually run the code, then worked in the order the brief set: repository and assumptions first, then schema, core services, pages, tests, UI.
**Problem:** none at this step.

### 2. Core services (claim / redeem transactions)
**Action:** wrote `claim_code()`, `redeem_reward()`, `update_redemption()` with row locks, conditional updates and UNIQUE constraints, plus 61 business-rule tests including parallel-process race tests.
**Observation:** all 61 passed on the very first run. A race test that cannot fail proves nothing, so this was treated with suspicion rather than celebrated.
**Check:** the AI temporarily removed the `FOR UPDATE` locks and the `points_balance >= ?` guard from the redeem function. The race tests then failed as they should (all 8 simultaneous redemptions "succeeded" with only enough points for one). The original code was restored and the suite re-run (61/61).
**Lesson:** tests were validated by breaking the code on purpose.

### 3. MISTAKE — layout hack in `page_end()`
**What went wrong:** while writing the shared layout the AI decided whether to close the sidebar wrapper `<div>` by inspecting `ob_get_contents()` for the text `class="shell"`. It is fragile (output buffering may be off) and unreadable for a student to explain.
**Detected:** by re-reading its own file straight after writing it, before any test ran.
**Fixed:** replaced with an explicit flag set in `page_start()` (`$GLOBALS['lb_shell']`).

### 4. MISTAKE — three front-end bugs in `app.js`
**What went wrong:** (a) pre-filling dialogs set `select.value = undefined`, which would blank the "Product" dropdown of the Generate-codes dialog; (b) the dialog-title code would have turned "Generate codes" into "Add generate codes"; (c) after the Back button a submit button could stay permanently disabled.
**Detected:** by code review of the freshly written file (none was caught by a test yet). The browser test later confirmed the fixed behaviour ("Generate dialog keeps a product selected and title unchanged").
**Fixed:** skip selects when adding; only retitle dialogs that have an `id` field; reset loading state on `pageshow`.

### 5. MISTAKE — blur validation made the Submit click miss (found by a real failing test)
**What went wrong:** inline validation ran on `blur`. When a user typed in a field and clicked Submit, the blur fired first, an error line appeared and pushed the button down before the mouse was released, so the click landed on empty space and the form never submitted.
**Detected:** the headless-browser test "Register: inline errors for empty/short fields" failed — only the password field had an error, the others did not, because the form had never been submitted. It looked like a test problem; the AI reproduced it in a small debug script to confirm it was a genuine UX bug.
**Fixed:** skip blur-validation when focus is moving to a button; the submit handler validates every field anyway.

### 6. MISTAKE — a regex edit removed the main button, and the test could not notice
**What went wrong:** the brief says "one filled primary button per screen at most". After a screenshot showed several filled "Redeem" buttons, the AI edited all pages with a regex to un-fill empty-state buttons. The regex spanned too many lines and also un-filled the "Generate codes" button in the Codes page header.
**Detected:** by looking at the next screenshot (the header button was plain). The automated check passed because it only asserted "at most one" primary button, and zero satisfies that.
**Fixed:** restored the button, and changed the test to require the exact expected number of primary buttons per page (e.g. admin/codes = 1, customer/rewards = 0).

### 7. MISTAKE — a test that could not fail
**What went wrong:** while writing the UI tests the AI wrote `check('No inline style attributes…', count === 0 || true)`. The `|| true` made it always pass, and the check was also wrong in principle (JavaScript legitimately sets styles through CSSOM).
**Detected:** on re-reading the test file before the first run.
**Fixed:** replaced with a real check that the server-sent HTML contains no `style=` or `on…=` attributes.

### 8. Smaller test and tooling errors (all the AI's own)
* Started a test server with a different `CODE_PEPPER` than the tests use, so codes would not match.
* The HTTP test checked for a `Set-Cookie` header with a client that already held a cookie; the server correctly sent none. Test fixed to use a fresh client.
* The UI test opened `/customer/register.php` while signed in, which correctly redirects; test fixed to use a signed-out browser context.
* A `pkill -f "php -S …"` command matched its own shell and killed the sandbox shell; replaced with a pattern that cannot match itself.
* The MariaDB and dev-server processes were lost twice when the sandbox reset; a start script was added to restore them.
These did not affect the shipped application.

### 9. Visual review by the AI
**Action:** the AI rendered every page at desktop/tablet/mobile and light/dark in headless Chromium, then looked at screenshots. This found issues the tests could not: tiny chart labels (SVG scaled down), a chart card stretched to the height of its neighbour, a redundant second status filter on the Codes table, wrapped code cells, and Activate+Deactivate buttons both shown for every batch.
**Fixed:** all of the above.
**Limit:** the AI only viewed a few screenshots individually; it did not look at every one of the ~60 generated images. Visual quality beyond the checked items is not guaranteed.

### 10. User feedback — the install failed in phpMyAdmin (MISTAKE in the first delivery)
**Prompt (from the user, with a screenshot):** importing `schema.sql` in phpMyAdmin gave "#1046 - No database selected". Later: "tell me just simple solution", then "see this project that gave me before … in this project I don't get any error" (an earlier project, `visitor-slideshow`, was uploaded for comparison).
**What went wrong:** the first delivery assumed a terminal and a MySQL admin account. The schema file did not create the database, began with `DROP TABLE` (so importing twice would have wiped data), the first admin had to be created from the command line, and `CODE_PEPPER` had to be generated and pasted by hand. None of that suits a XAMPP/phpMyAdmin user, and I never tested the phpMyAdmin path.
**Detected:** by the user, not by any test. Comparing with the other project showed what they expected: one importable file that creates its own database, admin creation in the browser, a `check.php` page, defaults that match XAMPP.
**Fix:** `database.sql` now creates the database and uses `CREATE TABLE IF NOT EXISTS` (no drops); admin setup page; automatic `config/secret.key`; `check.php`; XAMPP defaults; `.htaccess` guards; a friendly "database is not ready" page; README rewritten around XAMPP.

### 11. MISTAKE — brand-new admin was signed straight out (found by a new test)
**What went wrong:** the idle-timeout code treated a session with no `last_seen` timestamp as expired. After the new browser setup page created the admin and redirected to the dashboard, the next request logged them out. Normal sign-in only worked because the login page happened to set the timestamp first. The same latent flaw was in the customer code.
**Detected:** the new HTTP test "The admin dashboard opens right after setup" failed (302 to login). The first guess was a test-client problem; printing the redirect target showed it was the application.
**Fixed:** only apply the timeout when a timestamp exists. Added direct tests for brand-new, 60-second-old and 4000-second-old sessions, and confirmed the new test fails against the old code.

### 12. Clean-room install check (Apache + MariaDB, following the new README)
**Action:** the final ZIP was unzipped into Apache's web folder under `/loyalbox/`, with `.htaccess` enabled, no `.env`, MySQL user `root` with an empty password (to imitate XAMPP), and `database.sql` imported **with no database selected, twice** (the phpMyAdmin scenario that failed for the user).
**Results:** both imports succeeded (11 tables, data kept). `check.php` listed what was missing before the import and showed all tables found after it. Opening `admin/` led to the setup page; creating the admin signed in straight to the dashboard; the setup page then redirected to login. Product creation, code generation (which created `config/secret.key`, 64 characters), customer registration, claim (+25 points) and a second claim of the same code ("already been used") all worked. Apache returned 403 for `config/secret.key`, `database.sql`, `README.md`, `src/config.php`, `tests/`, `scripts/` and `.env.example`, and 404 for `.git`.
**Two things found by this run:**
* The first attempt returned HTTP 500 on admin pages. The Apache log showed `1698 Access denied for root@localhost`. The cause was the sandbox's MariaDB (its root account uses socket authentication instead of an empty password), not the application. The sandbox was changed to match XAMPP.
* It did show a real gap: that kind of database-login error displayed a generic "Something went wrong" instead of the helpful "The database is not ready" page. Error codes 1130 and 1698 were added, and the README now tells users to put a MySQL password in `config/config.local.php`.
**Not verified:** real XAMPP on Windows or macOS, phpMyAdmin's own import button (the same SQL was imported with the `mysql` command), and a browser pointed at the Apache copy (the browser tests ran against PHP's built-in server).
